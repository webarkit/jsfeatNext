# Milestone 1.1.0 — GMS for the webarkit tracker

**Date:** 2026-10-14
**Status:** design, awaiting approval
**Milestone:** [1.1.0](https://github.com/webarkit/jsfeatNext/milestone/3)
**Builds on:** [`docs/features2d-expansion-plan.md`](../../features2d-expansion-plan.md) (decisions D1–D11)

---

## 1. Intent

The first consumer of 1.1.0 is the **planar tracker in `webarkit/webarkit`**.
Its practical bottleneck is the inlier ratio: today it feeds ratio-tested ORB
matches straight into the homography estimate, and RANSAC has to dig the
solution out of a lot of noise. GMS (Grid-based Motion Statistics, Bian et al.,
CVPR 2017) sits between matching and RANSAC and discards matches whose
neighbourhood does not move coherently with them. More inliers means fewer
RANSAC iterations, a steadier homography and less jitter in the anchored
content.

So 1.1.0 is **GMS and what GMS needs**, nothing more. The rest of the
features2d expansion (TEBLID, FREAK, tree-shaking) moves to 1.2.0: it is
valuable, but it is not what unblocks the tracker.

## 3. Goals, non-goals, anti-goals

**Goals**

- `jsfeatNext.gms` ships in `@webarkit/jsfeat-next@1.1.0` on npm.
- GMS is **bit-exact against OpenCV's `cv::xfeatures2d::matchGMS` on all four
  paths** — default, `withRotation`, `withScale`, and both together — so
  jsfeatNext can serve as PureCV's oracle for it (#96, D9).
- Its cost is **measured**, relative to the matching step it follows.
- Whoever wires #136 in `webarkit/webarkit` has everything they need once the
  release is on npm (§8).

**Non-goals**

- TEBLID, FREAK, tree-shaking, imgproc bench coverage (→ 1.2.0).
- Any change to `find_homography`, `motion_estimator` or `bfmatcher` behaviour.
- Any adapter code in jsfeatNext — the #136 wiring lands in
  `webarkit/webarkit`.
- LOGOS or any other geometric verification method.

**Anti-goals** — outcomes that would count as failure even if GMS "works":

- GMS validated with a tolerance or only by property tests. A partial oracle
  pushes the debugging into Rust + WASM (D2).
- Only the default path implemented or tested (D9).
- Any behavioural change to already-shipped modules, or a red parity suite.
- A new runtime dependency, or Python entering `npm ci` / CI.
- Any break of the `jsfeatNext.<module>` namespace API (post-1.0 that would
  mean a 2.0.0).
- GMS turning out more expensive than the matching step it is meant to make
  cheaper downstream, and shipping anyway without that being discussed.

### 5.1 #130 — OpenCV licence variant

For 1.1.0 the only consumer is `src/gms/**`. The mechanism must let TEBLID and
FREAK add their *own* upstream notices in 1.2.0 without restructuring — each
OpenCV-derived path maps to the notice of the file it was actually ported from.

**What the upstream actually says (verified 2026-10-14).**
`opencv_contrib/modules/xfeatures2d/src/gms.cpp` carries no licence text and no
copyright line of its own — only OpenCV's standard pointer: *"subject to the
license terms in the LICENSE file found in the top-level directory"*. That
`LICENSE` is **Apache-2.0** today. GMS was contributed in 2018, when OpenCV was
3-clause BSD; the project relicensed with 4.5.0. So #130's premise — "copy the
upstream file's notice" — has nothing to copy for GMS; the notice has to be
written.

**The source header alone does not reach consumers.** `package.json` `files`
is `["dist", "types"]` (npm adds the root `LICENSE` automatically), so `src/`
headers never ship. The only notice in the published bundle is the banner in
`vite.config.mts`, which today credits jsfeat/MIT only. Apache-2.0 §4(a) also
requires recipients to receive a copy of the licence.

**Both licences are open to us, and the maintainer chose Apache-2.0.**
`gms.cpp` is byte-identical (blob `c13ffe4`) in opencv_contrib 4.4.0, which
was BSD-3, and in 4.5.0 / master, which are Apache-2.0. Its last change
(2020-03-08) predates the relicensing. So the port could be taken from
either. Apache-2.0 wins because TEBLID has no choice: `beblid.cpp`, which
contains TEBLID, entered opencv_contrib on 2020-12-09, after the relicensing,
so it exists only under Apache-2.0. Choosing it now means #130 builds the
mechanism once, and every OpenCV port shares one licence. Apache-2.0 is
one-way compatible with LGPL-3.0-or-later.

**Why a notice is needed at all.** Using OpenCV as a test oracle (running
`opencv-contrib-python` and committing its outputs as fixtures) copies no
OpenCV code and imposes nothing. Writing `src/gms/gms.ts` does: reaching
bit-exactness means reading `gms.cpp` and reproducing its choices, and a
translation into another language is a derivative work. A clean-room
implementation from the paper alone was considered and rejected. It would turn
bit-exactness into blind trial and error against the fixtures, and anyone
opening `gms.cpp` while writing it would break the clean room.

**#130's scope for 1.1.0 therefore grows to three parts:**

1. **Source header** for `src/gms/**`: the LGPL base without the jsfeat
   attribution, plus a notice that the file is ported to TypeScript from
   `opencv_contrib/modules/xfeatures2d/src/gms.cpp`, OpenCV contributors,
   Apache-2.0. The "ported/modified" statement satisfies Apache-2.0 §4(b).
2. **Bundle banner**: an OpenCV / Apache-2.0 line added to the banner in
   `vite.config.mts`, next to the jsfeat/MIT credit, so the published `dist/`
   carries the attribution.
3. **Licence text in the package**: the Apache-2.0 text committed (e.g. under
   `LICENSES/`) and added to `package.json` `files`, to satisfy §4(a).
   opencv_contrib has no `NOTICE` file, so there is nothing further to
   propagate.

Verify the published tarball (`npm pack --dry-run`) lists the licence file.

### 5.2 #132 — OpenCV fixture harness

As written, with two amendments:

1. **`opencv-contrib-python`, not `opencv-python`.** `matchGMS` lives in
   `xfeatures2d`, which only ships in the contrib wheel. The README pins the
   exact version used.
2. **A generic fixture envelope.** The schema in the issue body is
   descriptor-shaped, but neither 1.1.0 consumer is a descriptor: the first
   fixture (`compute_integral_image` vs `cv2.integral`) outputs an integer
   array, and GMS consumes keypoints + matches and outputs a subset of matches.
   The harness therefore defines a common `meta` block (OpenCV version,
   algorithm, params, input image + sha256 where an image is involved) plus an
   algorithm-specific payload. The descriptor payload in the issue body becomes
   the TEBLID/FREAK payload in 1.2.0.

The integral fixture remains the first one, to validate the harness itself
before GMS depends on it. The implementing agent runs the generator itself, in
a venv with the pinned contrib wheel (§10).

### 5.3 #134 — GMS

As written, plus:

**API.** `jsfeatNext.gms` is a singleton. Its one public method mirrors
`matchGMS`'s argument order:

```ts
gms.filter(
    size1: { width: number; height: number },
    size2: { width: number; height: number },
    keypoints1: keypoint_t[],
    keypoints2: keypoint_t[],
    matches: match_t[],
    with_rotation = false,
    with_scale = false,
    threshold_factor = 6,
): match_t[]
```

It returns the kept matches **as a subset of the input, in input order**,
which is exactly what the `filterMatches` seam of the contract requires
(subset, indices preserved). Snake-case parameters follow `bfmatcher`
(`max_distance`, `cross_check`).

**No grid-size parameter.** The contract's `FilterOptions` has
`gridSize?: number` (reference default 20), but OpenCV hardcodes 20×20, so any
other value could not be pinned against the fixtures. Leaving it out is
reversible (adding a trailing parameter later is additive); adding it now and
removing it later would be a 2.0. The adapter rejects `gridSize ≠ 20` (§8).

**Cost must scale with the matches, not with the grid.** A literal port zeroes
and scans the dense `400 × N` motion-statistics matrix on every pass (N up to
40×40 on the scale path), and the full search makes 160 passes: on the order of
10⁸ operations, far over the ~33 ms frame budget. The internal structure must
make each pass proportional to the number of matches (e.g. count only the
occupied cell pairs), while reproducing OpenCV's results exactly — including
its tie-breaking when picking the best right cell for a left cell. This keeps
every path usable, so the choice of flags stays the caller's and does not
depend on what the implementation can afford.

**Fixtures — four paths, not three.** OpenCV's `run()` has four branches:
default, `withRotation`, `withScale`, and both together (the nested
scale × rotation loop). #134 names three; all four are pinned. GMS only looks
at keypoint positions, image sizes and the `queryIdx`/`trainIdx` pairs, so its
fixtures are pure geometry. The generator produces the second view in Python
from the committed image with a known transform — a translation for the
default path, an in-plane rotation for `withRotation`, a scale change for
`withScale`, both for the combined path — runs ORB + `BFMatcher` on both
views, injects a known share of wrong matches so the filter has something to
reject, and commits `size1`, `size2`, both keypoint sets, the matches and
OpenCV's kept-match indices. The second view itself is not committed: once the
keypoints and matches are committed, no image bytes are needed.

**Bit-exactness risk.** Upstream mixes `float` and `double` arithmetic in the
grid indexing (normalised points are `Point2f`; some offsets add a `double`
`0.5`). Plain JS `number` arithmetic can put a point in a different cell at a
boundary. Mirror the upstream precision with `Math.fround` wherever upstream
computes in `float` — verify against the actual `gms.cpp` source, not from
memory. The "keep the best configuration" comparison (`>` vs `>=`) is the other
tie-breaking spot; the fixtures pin it.

**Property test — relaxed.** #134 asks that "every discarded match is
genuinely inconsistent with the known translation". GMS does not guarantee
that: it drops whole cells that lack neighbourhood support, correct matches
included, and the right-cell index is not re-offset with the left grid, so
correct matches straddling a right-cell border can be dropped. The test keeps
the expansion plan's wording instead: on `cornerScene` under an exact
translation, the **post-filter inlier ratio is ≥ the pre-filter ratio**. The
#134 body edit (§7) makes this change.

**Bench (added acceptance criterion).** A `bench/gms.bench.ts` written against
the vitest 5 API, so after #219. jsfeat has no GMS, so the jsfeatNext-vs-jsfeat
ratio does not apply; instead use the **intra-library ratio** precedent from
`bench/README.md` ("yape06 costs N× fast_corners"). The workload is the
tracker's real one: ≤ 300 scene keypoints on one level, matched the way the
tracker matches (`bfmatcher.knnMatch` with k = 2 plus `ratio_test`, which is
what the adapter's `match(…, { ratio })` maps to). Time all four GMS paths
against that matching step in the same run, and record "GMS costs N× matching"
per path in #134 and in the README's *Current status* table. The tracker calls
`filterMatches` with no options today, i.e. the default path: if that path
costs more than the matching step itself, raise it in #134 before release
rather than shipping silently.

**Docs.** TSDoc with a usage example on `gms.filter`; `gms` added to the README
module list; `AGENTS.md` module count and roadmap pointers updated; the
API-shape test and the API-surface parity test (#45) accept `gms` as a
jsfeatNext-only symbol, as they already do for `bfmatcher`.

## 8. The #136 work (code in `webarkit/webarkit`)

whatever session the maintainer assigns it to. What that work needs to know:

- **When:** after `@webarkit/jsfeat-next@1.1.0` is on npm.
- **Dependency:** `packages/cv-backend-jsfeatnext` pins
  `@webarkit/jsfeat-next` at `^0.17.0`, which excludes 1.x. That bump is
  already tracked by
  [webarkit/webarkit#94](https://github.com/webarkit/webarkit/issues/94)
  (for 1.0.0); it should target `^1.1.0` directly, or be followed by a bump to
  it.
- **Scope:** `capabilities.matchFilters` declares `"gms"` (the spec's only
  `MatchFilterKind`); `filterMatches` is implemented over
  `jsfeatNext.gms.filter(...)`, mapping `thresholdFactor`, `withRotation`,
  `withScale`; the adapter test that currently pins "declares no match
  filters, and omits the optional method entirely" is updated accordingly.
- **`gridSize`:** `gms.filter` has no grid-size parameter (§5.3). Per the
  contract's negotiation rule, the adapter accepts an omitted `gridSize` or
  `20`, and throws `UnsupportedCapabilityError` for any other value — never
  silently ignores it.
- **The tracker is already wired:** `packages/nft-tracker/src/detection.ts`
  calls `filterMatches` when the backend has it, with no options — so it gets
  the default path as soon as the adapter advertises GMS.
- **Out of scope:** exposing TEBLID/FREAK through `describe()` — that is the
  new 1.2.0 issue (§7).
- **Success measure:** the tracker, run on the same sequences with and
  without `filterMatches`, shows a higher inlier ratio. This is the success
  criterion for #136 and for the milestone's purpose, not a gate on the
  jsfeatNext release.

## 10. Decisions

**The maintainer's**

- The first consumer is the `webarkit/webarkit` tracker, which needs GMS for
  more inliers.
- 1.1.0 is GMS only; TEBLID and FREAK move to 1.2.0.
- The new GitHub project covers 1.1.0 only.
- #136 stays in jsfeatNext.
- The GMS port is licensed from OpenCV under **Apache-2.0**, with the notice in
  the source header, the bundle banner and the shipped package (§5.1).
- #136 stays on milestone 1.1.0; the milestone closes after the adapter wiring,
  not at the release (§9).
- The OpenCV fixture generator is **run by the implementing agent**, in a
  Python venv outside the repository (e.g. the session scratchpad), with
  `opencv-contrib-python` installed from PyPI at the pinned version. The
  maintainer has authorised that install. No venv, wheel or cache is
  committed; `tests/fixtures/opencv/README.md` documents the exact commands so
  anyone can repeat it.

**The designer's** — open to override:

- #219 and #225 join 1.1.0; #137 and #168 move to 1.2.0 with TEBLID/FREAK;
  #171 stays out.
- `gms.filter(...)` as the method name and shape, with no grid-size
  parameter (§5.3).
- An internal structure whose cost scales with the matches, so every flag
  combination is affordable (§5.3).
- Four fixture paths instead of three; the relaxed property test (§5.3).
- A GMS bench on the tracker's real workload, with an intra-library ratio, as
  an acceptance criterion of #134.
- The generic fixture envelope and the contrib wheel in #132.
- #136 re-scoped to GMS; its TEBLID/FREAK half becomes a new 1.2.0 issue in
  jsfeatNext.
- Project name, fields, priorities, the draft release item, linking both repos.
- No due date on 1.1.0 or 1.2.0.
- Comments on issues rather than body rewrites, except #130, #132, #134, #136.
